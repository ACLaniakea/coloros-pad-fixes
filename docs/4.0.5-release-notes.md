# 4.0.5 发布说明

本版只有一处行为变更，在 `OplusBSP-Modules` 里：**撤销我们对 zram_opt
swappiness 的覆盖，交还本机原厂值**。其余模块随统一版本号重新构建，内容未变。

---

## 撤销 swappiness 覆盖

### 原本做了什么

`oplus-bsp-module/service.sh` 在开机后一律写：

```
direct_swappiness=60
vm_swappiness=125
swapd_swappiness=125
dynamic_swappiness = 125 0 125 0
```

注释给的理由只有一句"对照机 PKX110 的 osvelte profile 解析成 125/60"。

### 为什么这是错的

这是纯粹的对齐论据，没有任何实测支撑，而且照搬错了对象：

- **本机自己的原厂脚本** `/product/bin/init.oplus.nandswap.sh` 里写的是
  `vm_swappiness=160`、`direct_swappiness=60`；
- **swapd 专用的那一档也被一并压低**：zram_opt 模块默认
  `g_hybridswapd_swappiness = 200`，被我们改成 125。swapd 是 hybridswap 里
  专门负责把冷内存搬进 zram 的线程，它本该是最偏向匿名页的；
- 对照机那个 125 是**它自己的脚本按机型分档算出来的**——同一个脚本里还有
  `vm_swappiness=100` 与 `200` 的分支，本来就不该跨机型照抄。

方向上这一手也是不利的：swappiness 越高越偏向回收匿名页、越多东西进 zram。
把 vm 从 160 压到 125、把 swapd 从 200 压到 125，等于让这台内存最紧的机器
更不敢用 swap，与"后台一多就掉帧、swap 用量上不去"的现象方向一致。

### 现在的行为

什么都不做：`vm`/`direct` 由产品脚本负责，`swapd`/`kswapd` 用模块默认。
只读一次记进日志便于核对。重启后实测：

```
vm_swappiness: 160   direct_swappiness: 60
swapd_swappiness: 200   kswapd_swappiness: 160
dynamic: 0 0 0 0        （模块默认，不启用动态分档）
日志: zram_opt policy left to stock: ...
```

### 收益尚未测得

这次改动的意义就在于一个可测的结果，但**目前只有刚开机的样本，不足以下结论**。
要判断需要一段正常使用后的稳态数据：swap 占用、`pswpin`/`pswpout` 速率、
`pgsteal_kswapd`，以及 `swapd_shrink_anon` 有没有真的变多。

## 顺带查清、但确认为原厂行为、因此不动的

这一轮把内存链路整条对照了一遍，记下来免得以后重复排查。

| 项 | 本机 | 对照机 | 结论 |
| --- | --- | --- | --- |
| `watermark_scale_factor` | 80 | 50 | **不动**。80 来自联想自己的 `/vendor/bin/init.kernel.post_boot-memory.sh` 第 35 行，是这台硬件的 vendor 原厂值；对照机那份是 OPlus 改过的分档版本 |
| `min_free_kbytes` | 11584 | 23168 | **不动**。同上，由同一个 vendor 脚本按标准公式算出并经 `vendor.memory.min_free_kbytes` 属性写入 |
| zram 压缩算法 | lz4 | zstd | **不动**。`comp_algorithm="lz4"` 在本机原厂 nandswap 脚本里是写死的，lz4 就是这套移植包的原厂选择 |
| `avail_buffers` | 2300/2000/2300 | 2500/2200/2500 | **不动**。两机的脚本分档都是 2200/1800/2200，实机值都是 QTI perf HAL 在运行时按内存容量抬上去的，原厂让它抬 |
| 其余 hybridswap 参数 | — | — | `zram_wm_ratio`、`stored_wm_ratio`、`compress_ratio`、`cpuload_threshold`、`area_anon_refault_threshold`、`swapd_max_reclaim_size`、`swapd_shrink_parameter`、`swapd_memcgs_param` 等**两机逐项相同** |
| `/proc/sys/vm/swappiness` = 100 | 100 | 125 | **不动**。zram_opt 注册了 `android_vh_tune_swappiness`，`zo_set_swappiness()` 在回收路径上无条件覆盖，这个 sysctl 不参与决策，只是显示值 |

## 这一轮顺带弄清的机制

- swapd（hybridswap 的主动回收线程）有三重闸门：**熄屏完全不工作**
  （`if (atomic_read(&display_off)) return;`）、buffers 高于 `min_avail_buffers`
  就跳过、干起来还限速 `swapd_max_reclaim_size=50MB` / 1000ms 窗口。这些都是原厂设定。
- `system_cur_avail_buffers()` 算的是 `空闲页 - 保留页 + 文件页(扣掉一半或低水位)
  + 可回收 slab(同样扣一半)`，换算成 MB。所以文件缓存多的时候 swapd 会认为内存宽裕。
- 压力真来的时候是 kswapd 在干活：实测忙碌时段 `pgsteal_kswapd` 达 6258 页/秒
  （约 24MB/s），而 `pswpin` 与 `workingset_refault_anon` 完全相等——**换出去的匿名页
  100% 立刻被读回**，是纯抖动。抖动是阵发的，跟着使用走，不是常态。
- 后台冻结是**在工作的**，走 cgroup v1（`/dev/freezer`），不是 AOSP 的 v2 路径。
  `dumpsys activity` 显示 `use_freezer=true`、`freezer_cutoff_adj=900`，即只有
  `oom_score_adj ≥ 900` 的进程才会被冻。
