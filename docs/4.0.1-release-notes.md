# v4.0.1

v4.0.1 是 v4.0.0 稳定基线之上的修正发布：全部正式模块与配套 APK 统一为 `4.0.1 / 400001`，由当前源码重新构建。

> [!NOTE]
> 本次**未变更内核**。Release 中的 `boot-ACLaniakea-SM8650Q-droidspaces-r1.img` 与 `vendor_boot-hyperSched-stub.img` 与 v4.0.0 内容相同，仍须成对刷入。

## 相比 v4.0.0

### 前台掉帧（本次主要改动）

桌面滑动掉帧率从 **12.49% 降到 6.23%**，帧时间 p99 从 **150ms 降到 48ms**。

定位过程：`gfxinfo framestats` 逐阶段拆解把病灶指向调度，而非 GPU（帧内中位仅 1.29ms）或内存（PSI `some avg60` 仅 0.10）——`Vsync→HandleInput` 这一段纯调度延迟 p99 达 6.92ms，而 144Hz 的帧预算只有 6.95ms，光等 CPU 就吃满整帧。

根子在核心拓扑：本机是六核 1+4+1，`cpu0` 是**唯一**的 A520，实测 65% 忙，还承接了全部 WiFi 收包中断（本机无本地调制解调器，蜂窝来自通讯共享）。而 `top-app` 的 cpuset 原本是 `0-5`，UI 线程一旦落到 `cpu0` 就得排队。

改动是让 `top-app` 沿用原厂给 SurfaceFlinger（`sf` 分组）的那套核集合——原厂本来就把 `cpu0` 从 `sf` 排除了，说明它也认定延迟关键的工作不该放那颗核——并打开 `latency_sensitive`，让调度器唤醒时优先找空闲核。代价是 `top-app` 可用核从 6 降到 5，换掉的是最弱且最忙的那颗。

按帧数归一后：`Missed Vsync` −53%、`Slow UI thread` −48%、`Slow issue draw commands` −59%、`Slow bitmap uploads` −77%。

### 手写笔触感反馈

原厂触感反馈页上的三个控件在这支笔上全是死路：书写反馈与振动强度写的是 ColorOS 专有特征，本机 GATT 里没有；功能反馈的原厂接口是个只打日志的空实现。现在这三行连同试写区一并隐藏，改由一个直连联想触觉通路的**全局书写反馈**开关，加**五档笔触感模式**（铅笔／钢笔／圆珠笔／马克笔／齿轮）代替。触感反馈入口跟随连接状态置灰，与同页其它行一致。

传输层同时修正两处会导致「振动整体消失」的问题：

- 不再把原厂书写开关命令翻译到联想的触觉**总开关**特征——那条命令带关闭语义时会让笔上所有振动断电，且只有重新服务发现才能恢复；
- 会话查找改为优先返回仍绑定在活动会话上的那一个。重连后残留的同 MAC 孤儿会话会让命令永远无人认领，1.8 秒后看门狗判死整条传输。

### system_server 的 AOT 产物失配（本次新增）

移植包里 `/system/framework/services.jar` 的主 dex 被换过（zip CRC 变了），配套的 oat 产物没有重建。ART 校验 `services.vdex` 里五个 location checksum 时只有主 dex 那个对不上，而它要求**全部**匹配，于是整份拒绝，退回从 jar 直读原始 dex —— system_server 的主体（18MB dex）一直在解释执行加 JIT。

代价是可量化的：`Jit thread pool` 累计占开机时间的 **5.4%**，同代 ColorOS 对照机是 0.167%；解锁瞬间 JIT 独占 system_server CPU 的 20.2%，并连带推高内存回收压力（每次直接回收要刨 58.3 页，对照机 18.4 页）。

系统自身修不了这个：`odrefresh` 只检查文件存在性与 ART apex 版本，因此报告 “system_server artifacts on /system OK” 而从不重编；它编到 `/data/misc/apexdata` 的产物又会在下次开机被自己当作多余清理掉（实测三次重启均如此）。同一个 checksum 也让 `services.jar.prof` 失效，所以默认的 `speed-profile` 只能产出 0.2MB 的空壳。

本版直接随包分发已编译好的产物，由 `post-fs-data` 绑定到 `/system` 侧，**相同移植构建的设备安装后重启即生效**，无需等待本机编译。

产物有效的条件是 `services.jar` 的 zip CRC、boot 镜像链、`BOOTCLASSPATH` 组成与 class loader context 四项与编译时一致——这些都由 ROM 构建决定，同一移植包刷出来的设备必然相同。若构建不同，ART 会拒绝这份产物（表现与修复前一致，不会更糟），此时模块会在开机完成三分钟后于后台自动重编：判据是 system_server 有没有真的映射 `.odex`，boot 镜像链、`BOOTCLASSPATH` 与 class loader context 全部从运行中的系统读取，不硬编码机型，编译只发生一次并有失败次数上限，产物在下次开机生效。

因此 `FixModule` 体积由 89.8MB 增至 127.9MB。这三项参数缺一不可，注释里记录了完整的 `dex2oat` 命令：`--compiler-filter=speed`（`speed-profile` 因 profile 与 jar 同源失效只出空壳）、`--boot-image` 必须是双组件链、以及 `--class-loader-context`——缺最后一项时 ART 的表现是收下 vdex 却拒绝 odex，极易误判为校验失败。

> [!NOTE]
> **已确认**：三个产物（`.art` / `.odex` / `.vdex`）全部被 ART 采纳，连续重启可复现，产物头部的 class loader context 与正常设备逐字节一致。
> **尚未确认**：对解锁掉帧与 system_server 占用的实际改善幅度。采样窗口内有用户交互干扰，未取得干净的稳态对照，因此本说明不宣称具体收益数字。

### 稳定性与开销

- **收敛充电控制节点权限**：移植包把 `charging_enable`、`charge_control_limit` 与 `usb/real_type` 一律开成全局可写，任何应用都能停掉本机充电。现在去掉 other 的写位，属主与读权限不变，原厂充电保护与移植包自带的守护进程两条既有写入路径都不受影响。
- **应用建议自愈改为限速**：原先的文件监视假设主库只在数据库替换时变动，实测本机每 2.7 秒就触发一次，等于持续以 0.37Hz 启动 ART 虚拟机做无事发生的检查。改为验证本身限速后，系统空闲期进程创建速率从 42/s 降到 19~24/s。
- **键盘自定义键**：「选择应用」页的「显示系统应用」开关此前点了没反应，现在就地重过滤列表。

## 已知问题

移植包重打包 vendor 时丢了两个可执行文件的 SELinux 标签（`/vendor/bin/qms`、`/vendor/bin/qcc-vendor`），导致 init 拒绝注册对应服务，`servicemanager` 会持续尝试惰性启动五个射频/数据 AIDL 接口并失败。因本机没有本地调制解调器，**功能上没有损失**，但会产生约 5 次/秒的无效 init 往返。这属于打包阶段缺陷，KernelSU 模块无法修复（init 解析 rc 早于模块挂载），须在重打包时对 `vendor_file_contexts` 执行一次 `setfiles`。

## 安装或升级

请使用同一 v4.0.1 Release 的产物。内核沿用 v4.0.0，不需要重刷；其余模块与 APK 均已随本版本重新构建。

安装完 KernelSU 模块与 APK 后执行一次**完整重启**，不要仅重启 zygote。
