# v4.0.2

v4.0.2 是 v4.0.1 之上的修正发布。全部正式模块与配套 APK 统一为 `4.0.2 / 400002`，
由当前源码重新构建。内核与 boot 沿用 v4.0.0/v4.0.1，**不需要重刷**。

本版只有两处功能改动，其余模块仅为版本对齐重建。

---

## 1. ZUI 相机在其他设备上闪退（重要）

有用户反馈相机一打开就闪退。崩溃日志的根因是：

```
java.lang.NullPointerException: getSupportedModes() must not be null
    at com.zui.camera.ui.mode.ModeRecyclerView.generateModeList(ModeRecyclerView.kt:241)
    at com.zui.camera.ui.mode.ModeRecyclerView.<init>(ModeRecyclerView.kt:137)
```

ZUI 相机按 `Build.DEVICE` 在内置 JSON 里查本机支持哪些拍摄模式，查不到就返回 null，
Kotlin 空断言直接抛 NPE。相机模块里的 zygisk 身份层本应把该进程的机型属性改写成
Lenovo，但它**把开发机上 `com.zui.camera` 的 UID 写死成了常量**。UID 由安装顺序
决定，换一台设备就对不上，身份层不生效，相机读到的仍是移植包的 `OP6547L1`。

4.0.2 改为在 `postAppSpecialize` 读 `/proc/self/comm` 按进程名识别。该值由 AOSP 的
`SpecializeCommon()` 在这一步之前设好，读它不需要任何权限，因此与设备、与 zygisk
实现（Magisk / ReZygisk / Zygisk Next）都无关。注册也改为 ABI v4→v3→v2 逐级回退，
被拒时不再静默失效。

实机验证：相机进程的 `build_prop` 映射为 `rw-p`（私有 COW，补丁生效），SystemUI 为
`r--s`（未被误伤）。

> 这不是 hybrid_mount 或 OverlayFS 的问题——先前的推测已被崩溃日志推翻。

## 2. 8GB 内存档（修复模块）

**症状**：长时间锁屏后点亮，锁屏动态壁纸和解锁动画明显卡顿。

**测量**：息屏 120 秒后点亮的 6 秒窗口内，系统换入 712 MB、直接回收 573 MB。
直接回收发生在申请内存的那个线程的上下文里，也就是 UI 线程被同步阻塞。
按进程拆分后，桌面、SystemUI、system_server 三者合计有 1 GB 以上躺在 zram 里。

**原因**：ColorOS 的 swapd 按 `app_score` 分级，`score 100-399` 这一档允许把 80%
的内存压进 zram，而所有 memcg 分组默认都停在 300。**这一点在原厂 ColorOS 上也一样**
（已用真机 ColorOS 对照确认），所以不是移植缺陷。

问题在于：原厂把 `min_free_kbytes`、`avail_buffers` 都按内存容量分了档，
**唯独这个 80% 的压缩比例不随内存大小变**。同一个策略在 11GB 机器上还剩 3.5 GB
余量，在 7.4 GiB 的本机就开始抖动。

**改动**：在 `RamSizeGB <= 8` 的设备上，把 `/apps/active` 与 `/apps/systemserver`
两个原厂分层组的 `app_score` 写为 0（即 level 0，不压缩）。
`/apps/inactive` 保持原厂 300 —— 那里装着几十个纯缓存应用，整桶豁免等于在 8GB
机器上放弃 swap。12GB 及以上的设备完全保持原厂行为。

**实测（同一次开机内 A/B，息屏 90 秒后唤醒）**：

| 指标 | 原厂 (score=300) | 本档 (score=0) |
|---|---|---|
| 换入 `pswpin` | 58.6 MB | 17.6 MB（−70%） |
| 直接回收 `pgsteal_direct` | 79.7 MB | **0** |
| 主缺页 `pgmajfault` | 15731 | 5127（−67%） |

代价：`MemAvailable` 约 −200 MB，两组用量收敛，零 LMK/OOM 击杀。

> 这是**主动偏离原厂**，不是恢复原厂。若出现后台应用留存变差或击杀增多，
> 第一个该回退的就是这里：把两组 `app_score` 写回 300 即可。

## 已知问题（沿用 v4.0.1）

- `/vendor/bin/qms` 与 `/vendor/bin/qcc-vendor` 的 SELinux 标签在 vendor 重打包时
  丢失，init 因此丢弃这两个服务，5 个射频 HAL 接口缺失。只能在打包阶段用
  `setfiles` 修正，模块侧无法弥补。

## 关于 `payload/bin/` 下的 post_boot 副本（不是缺陷）

`payload/bin/init.kernel.post_boot.sh` 与 `init.qcom.post_boot.sh` 里写的
`min_free_kbytes=65536`、KGSL `page_reclaim_per_call=1024` 等值**不会生效，这是设计如此**。

这两个脚本的 bind 补丁早先已撤销（见 `post-fs-data.sh` 中的说明）：当初打补丁是为了
压住「本机没有一加内存栈」时的换入风暴，后来 BSP 模块补齐、前提消失，就改回让原厂
脚本说了算——OSense 与 hybridswap 的调参都是以原厂基线为准的。副本保留仅为回滚备用。

实测现状（均为原厂值，正确）：`min_free_kbytes=11584`（与 `vendor.memory.min_free_kbytes`
属性一致，由原厂 `init.kernel.post_boot-memory.sh` 的 `RamSizeGB>=8` 分支写入）、
`watermark_scale_factor=80`、`swappiness=100`、KGSL `page_reclaim_per_call=38400`。

## 升级方式

请使用同一 v4.0.2 Release 的产物。内核与 boot 沿用 v4.0.0，不需要重刷；
其余模块与 APK 均已随本版本重新构建。
