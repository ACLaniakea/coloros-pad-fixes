# v4.0.2

v4.0.1 之上的修正发布：全部模块与配套 APK 统一为 `4.0.2 / 400002`。两处功能改动，其余模块仅为版本对齐重建。

> [!NOTE]
> 本次未变更内核。`boot` 与 `vendor_boot` 沿用 v4.0.0，**不需要重刷**。

## 相比 v4.0.1

### ZUI 相机在其他设备上闪退

有用户反馈相机一打开就闪退，崩溃日志的根因是：

```
java.lang.NullPointerException: getSupportedModes() must not be null
    at com.zui.camera.ui.mode.ModeRecyclerView.generateModeList(ModeRecyclerView.kt:241)
```

ZUI 相机按 `Build.DEVICE` 在内置 JSON 里查本机支持哪些拍摄模式，查不到就返回 null，Kotlin 空断言直接抛 NPE。相机模块的 zygisk 身份层本应把该进程的机型属性改写成 Lenovo，但它**把开发机上 `com.zui.camera` 的 UID 写死成了常量**——UID 由安装顺序决定，换台设备就对不上，身份层不生效，相机读到的仍是移植包的 `OP6547L1`。

现改为在 `postAppSpecialize` 读 `/proc/self/comm` 按进程名识别。该值由 AOSP 的 `SpecializeCommon()` 在这一步之前设好，读它不需要任何权限，因此与设备、与 zygisk 实现（Magisk / ReZygisk / Zygisk Next）都无关。注册改为 ABI v4→v3→v2 逐级回退，被拒时不再静默失效。

> 这不是 hybrid_mount 或 OverlayFS 的问题——先前的推测已被崩溃日志推翻。

### 8GB 内存档

**症状**：长时间锁屏后点亮，锁屏动态壁纸与解锁动画明显卡顿。

**测量**：息屏 120 秒后点亮的 6 秒窗口内，系统换入 712MB、直接回收 573MB——直接回收发生在申请内存的那个线程上下文里，即 UI 线程被同步阻塞。按进程拆分后，桌面、SystemUI、system_server 三者合计有 1GB 以上躺在 zram 里。

**原因**：ColorOS 的 swapd 按 `app_score` 分级，`score 100-399` 这档允许把 80% 内存压进 zram，而所有 memcg 分组默认停在 300。**已用真机 ColorOS 对照确认原厂同样如此，所以不是移植缺陷**；问题在于原厂把 `min_free_kbytes`、`avail_buffers` 都按内存容量分了档，唯独这个压缩比例不随内存变。同一策略在 11GB 机器上还剩 3.5GB 余量，在 7.4GiB 的本机就开始抖动。

**改动**：仅在 `RamSizeGB <= 8` 的设备上，把 `/apps/active` 与 `/apps/systemserver` 的 `app_score` 写 0（level 0，不压缩）。`/apps/inactive` 保持原厂 300——那里装着几十个纯缓存应用，整桶豁免等于在 8GB 机器上放弃 swap。12GB 及以上完全保持原厂行为。

同一次开机内 A/B（息屏 90 秒后唤醒）：

| 指标 | 原厂 `score=300` | 本档 `score=0` |
|---|---|---|
| 换入 `pswpin` | 58.6 MB | 17.6 MB（−70%） |
| 直接回收 `pgsteal_direct` | 79.7 MB | **0** |
| 主缺页 `pgmajfault` | 15731 | 5127（−67%） |

代价：`MemAvailable` 约 −200MB，两组用量收敛，零 LMK/OOM 击杀。

> [!WARNING]
> 这是**主动偏离原厂**，不是恢复原厂。若出现后台应用留存变差或击杀增多，第一个该回退的就是这里：把两组 `app_score` 写回 300 即可。

### 修复与打包

- `exempt_persistent_memcg` 原实现只写 `/dev/memcg/apps/uid_$uid`，而本机是 per-package 布局、该路径仅存在一个空组，整段是空转的；现改为从 `/proc/PID/cgroup` 读进程实际所在的 memcg。
- 同一函数靠进程发现会漏掉开机时尚无 SystemUI 的 `/apps/active`，改为显式对齐两个原厂分层组。
- `build_all.sh` 补上把相机两个产物汇总到顶层 `releases/` 的步骤（v4.0.1 是手工拷的），并生成 `SHA256SUMS`。

## 已知问题

沿用 v4.0.1：移植包重打包 vendor 时丢了 `/vendor/bin/qms` 与 `/vendor/bin/qcc-vendor` 的 SELinux 标签，须在重打包时对 `vendor_file_contexts` 执行一次 `setfiles`。本机无本地调制解调器，功能上无损失。

## 安装或升级

请使用同一 v4.0.2 Release 的产物。内核沿用 v4.0.0，不需要重刷。

安装完 KernelSU 模块与 APK 后执行一次**完整重启**，不要仅重启 zygote。
