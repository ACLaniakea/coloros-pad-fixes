# v4.0.3

调度与 SELinux 两条链的修复发布：全部模块与配套 APK 统一为 `4.0.3 / 400003`。

本版的主线是一个此前没被发现的事实 —— **移植包里 OPlus 的负载均衡从开机起就没跑过**。

> [!NOTE]
> 本次未变更内核镜像。`boot` 与 `vendor_boot` 沿用 v4.0.0，**不需要重刷**。
> 新增的 `oplus_lb_bridge.ko` 由 OPlus BSP 模块在 post-fs-data 装载，不进内核镜像。

## 相比 v4.0.2

### sched_assist 的负载均衡从未被触发过

`/proc/oplus_scheduler/sched_assist/lb_stat` 的全部计数长期为 **0**。同 ColorOS 版本的对照机 PKX110 跑 26 小时是：

```
tick_hit     24,803,944        newidle_hit    114,913,338
```

`tick_hit` 基本等于调度 tick 次数，为 0 意味着函数体一次都没进过。

反汇编 `oplus_cpu_sched_sched_assist.ko` 后原因清楚了：

1. `__oplus_tick_balance` 与 `__oplus_newidle_balance` 在 `__ksymtab` 里，是**导出给外部模块调用**的入口，模块内部没有任何调用者；
2. sched_assist 自己注册的 `android_vh_scheduler_tick_handler` 只在 debug 打开时做 systrace，不碰负载均衡；
3. 入口处的门读的是 `lb_enable`，运行时值为 1 —— **门是开的，只是没人进**。

调用方是 **OPlus 打过补丁的 WALT**。对照机的 `sched_walt` 出现在 `oplus_bsp_sched_assist` 的使用者列表里，本机的不在；kallsyms 里 walt 符号数 **3177（本机）对 4164（对照机）**。本机内核带的是高通原版 WALT，不会去调那两个入口。

后果是 UX 线程（动画、输入、渲染）不会被主动迁到空闲核 —— 长期被归因为「亮屏一刻卡」「锁屏动画卡」的那类现象，机制上就在这里。

**做法**：新增自编内核模块 `oplus_lb_bridge`，把 tick 入口接回 `android_vh_scheduler_tick`。

修复后（本机 65 分钟 / 对照机 28 小时，同口径）：

| 指标 | 本机 修复前 | 本机 修复后 | 对照机 PKX110 |
|---|---|---|---|
| `tick_hit` / 秒 | 0 | **345** | 274 |
| `tick_pull_runnable_ux` | 0 | **22,037** | 9,834 |
| `newidle_hit` | 0 | 0 | 114,913,338 |

> [!NOTE]
> newidle 那半边接不了：`android_rvh_sched_newidle_balance` 是**受限 hook**，GKI 的
> `android_rvh_probe_register()` 在 static key 已翻起时返回 `-EBUSY`，即只允许一个探针，
> 而高通 WALT 已经占用。本模块只接 tick 这一半。

实现上踩了一个坑，记录下来：第一版把 `__oplus_tick_balance` **直接**注册成探针，insmod 瞬间 panic ——

```
Kernel panic - not syncing: Oops - CFI: Fatal exception in interrupt
__oplus_tick_balance+0x0/0x354 at __traceiter_android_vh_scheduler_tick+0x40/0x68
```

崩在进入函数体之前，是 kCFI 拦的。`__traceiter_*` 通过函数指针间接调用探针会校验目标的 kCFI 类型标识前缀，而该函数在 OPlus 源码里只被直接调用、地址从未被取过，编译器没给它生成那个前缀。改为在模块内加一层签名一致的转接函数、转接体里**直接调用**即可 —— 直接调用不走 CFI 校验。

三级撤销：`echo 0 > /proc/oplus_scheduler/sched_assist/lb_enable`（免重启）→ `rmmod oplus_lb_bridge` → 从模块清单删掉该行。

### 移植时丢掉的 SELinux 放行

对照机 3.5 个月的日志里 `avc: denied` 合计 **10 条**，且全是良性的 zygote socket。本机 **20 分钟 323 条**，其中 331 次判定里除 2 条外全是 `permissive=0` —— 真的在拦。

被拦的两类正好是上一节那条链的另一半：

```
untrusted_app / untrusted_app_all -> oplus_scheduler_sched_assist_proc  {read write}  (im_flag, ux_task)
surfaceflinger                    -> oplus_ux_task_app_proc             {read write}
system_app / system_server        -> proc_frame_boost_sys_ctrl          {read write}
cameraserver / audioserver / …    -> proc_frame_boost_ctrl              {ioctl}
```

应用与系统服务把关键线程的 tid 写进 `ux_task` / `ux_task_app`，sched_assist 据此标 UX。**被拦就等于线程从未登记成功，均衡器接通了也挑不出它们来迁移。**其中 `surfaceflinger` 被拦在 sched_assist 目录门口这条影响最直接。

`/proc/oplus_frame_boost/*` 这组节点是本项目的 `ua_cpu_ioctl` 建出来的，标签对、策略里却没有对应 allow —— 属于「节点装回来了、规则没跟上」。

同批还补了两处与调度无关的：`system_server` 的 Athena 内存回收写入（`zygote_tmpfs` / `vndbinder_device`），以及 `audioserver` 读应用音频线程调度参数（实时优先级提升）。

修复后在负载测试下，上述三类拒绝**全部归零**。

> 中途发现 `untrusted_app_30` 是**独立的 SELinux 类型**而非 `untrusted_app` 的实例 ——
> AOSP 按 targetSdk 分出 `untrusted_app_25/27/29/30/32` 一串类型，逐个补是打地鼠。
> 最终改用 AOSP 自带的 `untrusted_app_all` 属性一次覆盖。

### 手势服务开机崩溃循环

`com.oplus.gesture` 在开机 13 秒内连崩 4 次，对照机全程零崩溃：

```
IllegalStateException: SharedPreferences in credential encrypted storage
                       are not available until after user is unlocked
  at ScreenOffGestureService.onCreate → ActionContentProvider.query
                                      → GestureUtil.getDefaultGestureSwitch
```

用户解锁前就有人查 `ActionContentProvider`，provider 去读自己的 SharedPreferences，撞上 CE 存储未就绪。

现有的 `getStorageContext` 钩子只覆盖了走它的那条路。本版补一条：锁屏期间把 `ContextImpl.getSharedPreferences` 改道到 DE 存储（靠 `isDeviceProtectedStorage()` 防重入），解锁后不再改道，读到的仍是原厂 CE 数据。`com.oplus.gesture` 已加入 Hook 的推荐作用域，**需在 LSPosed 里勾选后生效**。

### Soter Key 开机自愈

参照第三方模块「修复Key状态」的 Soter 流程重新实现并并入修复模块：等用户解锁 → 打开工程模式 RPMB 状态页 → 停 `vendor.soter` → `pm clear com.tencent.soter.soterserver` → 重启服务 → 再触发一次状态页。

两处有意偏离上游：服务名改为扫 `init.svc.*soter*` 而不是硬编码候选表；收尾补一次 `force-stop`，不把工程模式页面留在屏幕上。

开关：`persist.sys.aclaniakea.soter_fix=0` 整段跳过，`persist.sys.aclaniakea.soter_fix_ui=0` 只做 stop/clear/start。

> [!WARNING]
> **这是能力移植，不是已验证的故障修复。**本机没有任何证据表明 Soter 当前是坏的：
> logcat 全缓冲里 soter 相关 0 条、无 error，`vendor.soter` 一直 running。
> 若使用指纹支付后出现需要重新验证的情况，第一个该关掉的就是这里。
>
> RKP 那半边**有意不移植** —— 它要写 persist 分区、依赖本项目没有的 `KmInstallKeybox`
> 二进制，而本机的证明链本来就走 tricky_store。

## 已知问题

- **桌面显存偏高**：`com.android.launcher` 的 Skia 暂存渲染目标缓存长时间运行后可涨到约 900MB（对照机约 60MB）。真正的纹理缓存两台相同，差异全在暂存目标没被复用；`TRIM_MEMORY_COMPLETE` 只能清掉其中一小部分。这是桌面应用内部行为，系统属性层面没有对应旋钮，本版未处理。
- **属性枚举拒绝**：每次进程 spawn 会有一轮遍历全部属性上下文的读取，在受限域上产生一批 `avc: denied`。已确认是本机独有行为（对照机策略同样拒绝，只是从不发生这种枚举），但**未定位到发起者**。影响是日志噪声与少量 spawn 开销，不构成功能损坏。
- **锁屏动态壁纸打拍**：沿用 v4.0.2 的结论，`144 ÷ 60 = 2.4` 不整除导致的固定节拍，与性能无关，无解。
- 沿用 v4.0.1：移植包重打包 vendor 时丢了 `/vendor/bin/qms` 与 `/vendor/bin/qcc-vendor` 的 SELinux 标签，须在重打包时对 `vendor_file_contexts` 执行一次 `setfiles`。本机无本地调制解调器，功能上无损失。

## 安装或升级

请使用同一 v4.0.3 Release 的产物。内核沿用 v4.0.0，不需要重刷。

安装完 KernelSU 模块与 APK 后执行一次**完整重启**，不要仅重启 zygote。
