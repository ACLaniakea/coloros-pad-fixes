# 4.0.4 发布说明

本版只动两个包：`OplusBSP-Modules` 与 `FixModule`。主题是**把移植过程中被弄断的
AOT 与内存链路接回原厂形态**，其余模块随统一版本号重新构建，内容未变。

---

## 一、system_server 里 ColorOS 那半边一直在解释执行

### 现象与定位

平板空闲时 `system_server` 每秒上千次**文件**缺页（对照机 20 次/秒量级），
`/proc/meminfo` 的 `Mapped` 只有对照机的一半，代码页留不住。

顺着查到 `system_server` 的映射：

```
services.odex        52MB  filter=speed       cp=PCL[…provider.jar*…]  → 映射 3 段 ✔
oplus-services.odex  59MB  filter=everything  cp=PCL[]                 → 映射 0 段 ✘
                     /system/framework/oplus-services.jar 裸映射 3 段  ← 解释执行
oplus-service-jobscheduler.odex 1MB speed  cp 里 services.jar 校验和是旧的 ✘
```

ART 收下了 `.vdex`（校验结果）却拒收 `.odex`（编译产物），这是 class loader
context 不匹配的典型表现。`oplus-services.odex` 的头部写着：

```
compiler-filter = everything
classpath       = PCL[]
dex2oat-cmdline = dex2oat --dex-file=oplus-services.jar --compiler-filter=everything ...
```

裸命令行、没有 `--class-loader-context`、没有 `--compilation-reason`、没有
`--comments=app-name:…`——真正的 ROM 构建不会长这样。对照机同一位置压根没有这两个
文件（只有带 fs-verity 元数据的 `*.ocomp.*` 那套），它的 system_server 用的是
odrefresh 编到 `/data/misc/apexdata/com.android.art/dalvik-cache/` 的产物。

**完整成因**：移植者手工往镜像里塞了一批 `everything` 档的 odex，既因为缺 CLC 而被
ART 拒收，又因为"文件已存在"让 odrefresh 认为无事可做——平板的
`apexdata/.../dalvik-cache/arm64/` 是空的。原厂路径被堵死，替代品又不可用。

### 处理

`bin/art-oat-repair.sh` 从"只修 `services.jar`"改写为遍历整条
SYSTEMSERVERCLASSPATH。判据仍是"`system_server` 到底有没有映射对应的 `.odex`"，
class loader context 取该 jar 在 SSCP 中之前的所有 jar。镜像里只读改不了，所以
产物编到模块 payload，由 `post-fs-data` 绑定。

同时修掉三处会产出废品的 bug（前一版只是碰巧没暴露）：

1. `BOOTCLASSPATH` 原先用 `grep -ao 'BOOTCLASSPATH=[^ ]*'` 取。`/proc/pid/environ`
   是 NUL 分隔的，`[^ ]*` 不在 NUL 处停，会把后面的环境变量一起吞进来——实测取到
   5052 字符，真实值 2652。
2. 启动镜像链原先 `sort -u`。按字母序 `boot.art` 会排到**最后**（`-` 是 0x2D，
   `.` 是 0x2E），而主镜像必须在最前。顺序错了 dex2oat 会静默地不使用镜像，产物头部
   变成 `requires-image=false` + `bootclasspath-checksums=d/...`，运行时必被拒。
   改成保持 maps 里的出现顺序（即加载顺序）只去重。
3. 镜像名正则 `boot[a-z-]*\.art` 漏掉 `boot-QPerformance.art` 这类含大写的扩展镜像，
   21 项只取到 18 项。

产出后用 `oatdump` 自检 `requires-image` 与 `bootclasspath-checksums` 形态，
这三类错误不会再悄悄溜过去。

### 结果

```
                              修复前      修复后
oplus-services              odex段=0  →  odex段=3
oplus-service-jobscheduler  odex段=0  →  odex段=3
```

连续五次重启复现稳定。产物头部与被 ART 接受的那份逐项一致
（`bootclasspath-checksums = i;22/9fedd4da:i;29/3edf96c4`、`requires-image = true`、
classpath 带各 jar 校验和）。

### 构建指纹（为装到别的移植包上做的冗余）

包里自带的产物绑死这套 ROM。`art-oat-repair.sh` 现在会把输入（启动镜像与各 jar 的
体量）记成一行指纹，`post-fs-data` 绑定前逐项重算比对，对不上就跳过——装到别的
移植包上时什么都不做，由脚本在本机重编、下次开机再绑。绝不拿一份不匹配的产物去
盖掉人家本来好好的原厂产物。

> 实现细节里有个坑值得记：比对最初写成 `grep -q "…\( \|$\)"`，而 toybox 的 BRE
> 不支持 `\|` 交替，守卫会永远判定失配。已改用 `grep -E`，并做了正反向验证。

## 二、补回缺失的 `oplus_mm_proactive_compact`

一加 `kernel/mm` 21 个模块目录，之前出货 12 个。`proactive_compact` 漏掉的原因是它
目录里没有 Makefile，而 `sweep_oplus_modules.sh` 靠 `find -name Makefile` 找活，
直接跳过了。

它只读地算内存碎片度，导出 `/proc/oplus_mem/fragmentation_index`（格式
`是否碎片 hpage_order proactiveness`），自己不发起规整。完整链路是：

1. 内核模块导出 `fragmentation_index`；
2. ColorOS 框架读到 `is_fragmented=1`，置 `sys.oplus.vm.oplus_compact_memory`；
3. init 的 `on property:` 起 `oplus_compact_memory` 服务；
4. `/system_ext/bin/autochmod.sh` 里执行 `echo 1 > /proc/sys/vm/compact_memory`。

第 2~4 步平板上本来就齐，缺的只有第 1 步，所以补上之前这条链整条不通
（内核自带的 `vm.compaction_proactiveness` 也是 0）。补上后实测该节点从 `1 4 20`
变为 `0 4 20`，即规整确实在发生。

不使用任何 vendor hook，无 per-CPU 变量（不占 `PERCPU_MODULE_RESERVE`），
ABI 门禁 18 个符号 CRC 精确。

## 三、osvelte 的节点命名与 lmkd 重挂

`oplus_mm_mm_osvelte` 一直是加载着的，但它的 procfs 根目录与字符设备都叫
`osvelte_dbg` 而不是 `osvelte`：

```c
#if IS_ENABLED(CONFIG_OPLUS_FEATURE_MM_OSVELTE_DBG)
#define DEV_NAME "osvelte_dbg"
#else
#define DEV_NAME "osvelte"
#endif
```

我们的构建脚本对整棵树的 CONFIG 取并集（各模块开的宏不一致会让共享结构体布局对不上，
而 osvelte 被 `hybridswap_zram` 与 `uxmem_opt` 依赖，必须统一），`_DBG` 因此被打开。
单纯关掉它不行——`dma_buf` 与 `ashmem` 两个子目录也在同一个宏里，关了就一起没了，
而对照机两样都有。所以把 `DEV_NAME` 固定为 `osvelte`，`_DBG` 的功能保留。

后果本来是三条断链：

- `libresourcemanagerservice.so` 读 `/proc/osvelte/dma_buf/procinfo` 一无所获；
- `lmkd` 读不到 `/proc/osvelte/lowmem_dbg`；
- `/dev/osvelte_dbg` 落不到 `vendor_file_contexts` 里 `/dev/osvelte` 那条规则上，
  标签退化成默认的 `device:s0`（策略里 `osvelte_device` 这个类型本来就是齐的）。

改名后 `/dev/osvelte` 的属主、权限、标签与对照机逐项一致
（`crw-rw--w- system:system u:object_r:osvelte_device:s0`）。导出符号 9 个、
CRC 全部不变，依赖它的两个模块不受影响。

### lmkd 重挂（软件桥接）

`lmkd` 在开机 1.8s 启动，而我们的内核模块要等 `/data` 挂好才能在 `post-fs-data` 里
insmod，实测 8s 才装上。`lmkd` 对 osvelte 的探测是**开机一次性**的，失败后缓存
"osvelte is not supported"——实测把 `MemAvailable` 压到 1369MB、PSI avg10 到 11.67，
它依然不去开；官方的 `lmkd.reinit` 钩子也不重走这条探测。

唯一能接回去的办法是在节点就位之后让 lmkd 重启一次。`lmkd` 在 init.rc 里是
`critical` 服务，所以这段卡得很严：必须已 `boot_completed`、`/dev/osvelte` 必须存在、
lmkd 必须确实没持有它、每次开机最多一次、延时 45 秒、可用 `disable-lmkd-osvelte`
文件关掉。触发引导保护的门槛是「4 分钟内崩溃超过 4 次」，单次重启差得很远。

实测日志：

```
lmkd-osvelte: lmkd(pid=911) 未持有 /dev/osvelte，重启一次令其重新探测
lmkd-osvelte: 成功，lmkd(pid=4165) 已持有 /dev/osvelte
lmkd-osvelte: lmkd 已持有 /dev/osvelte，无需处理     ← 幂等守卫
```

**收益要说清楚**：这条链只用于 lmkd 杀进程时的信息转储，**不参与杀谁的决策**，
属于诊断与上报。真正影响决策的那条（媒体资源管理读 dmabuf 归属）在模块改名之后
已自己通了，不依赖本段。

## 四、被证伪与被更正的

诚实记录，免得以后重复排查。

| 一度以为 | 实际 |
| --- | --- |
| 应用层 AOT 也掉档了，桌面/设置/手势该升到 `speed` | **错**。对照机实测桌面就是 `speed-profile` 10MB、设置 `speed-profile`、手势 `verify`，平板本来就一致。已全部改回原厂档位 |
| 镜像里的 `everything` 是原厂选择，应当恢复 | **不是**。原厂产物头部都带 `compilation-reason = prebuilt`，那批 `everything` 一个都没有，是移植者手工编的。且 `everything` 产物大 1.8 倍，对这台"代码页留不住"的机器是反向的 |
| `dumpsys meminfo` 的 GPU 行缺 dmabuf 明细是 osvelte 导致的 | **无关**。装上 `/proc/osvelte` 后那行仍无拆分，那是 memtrack HAL 的事 |
| `/proc/oplus_resctrl/*` 被用户态引用，说明移除 `oplus_resctrl` 是错的 | **不是**。对照机同样没有这些节点，`liboplus_resctrl_psi.so` 与 `storaged` 引用的是它那边也不存在的路径。原决定成立 |

## 五、评估过但不做的

| 项 | 结论 |
| --- | --- |
| `mm_boost_pool` | 没有 `module_init`，是给厂商 dma-heap 驱动内联用的库，平板用的是联想/高通未改的 heap。且其"预填页池"能力本机已有等价物：`uxmem_opt` 的 `/proc/oplus_mem/ux_page_pool`（约 104MB）在跑 |
| `gloom` / `memleak_detect` | 要 GKI 与一加 common 树里都没有的 mm vendor hook，后者还要给 `struct vm_struct` 加 OEM 字段——结构体布局改动，模块侧做不到 |
| `thp_zsmalloc` | 唯一带 per-CPU 变量的候选，而 `PERCPU_MODULE_RESERVE` 已用满；还要改正在承载 hybridswap 的 zsmalloc |
| `oplus_mm_kevent{,_fb}` | 已编译、已过 ABI 门禁，**不出货**：本机无生产者也无消费者（mm/ 与 cpu/ 源码树里无人调用 `mm_fb_kevent_send_to_user`，已出货的 34 个 ko 也无人引用）。源码与构建配方留在 `kernel-compat/oplus_mm_kevent/` |
| `bsp_kevent` 守护进程 | 它连的是 `secureguard/keventupload` 的裸 netlink 协议号，与 `oplus_mm_kevent` 的 generic netlink 家族 `mm_fb` 不是一回事。本身只做 DCS/OLC 遥测上报，对性能无影响 |
| `vendor.qti.MemHal-service` | 闭源 QTI vendor 二进制，联想 vendor 里没有；跨 BSP 版本从对照机搬过来链不上 |
| `/proc/osvelte/gpu/procinfo` | 要 GPU 驱动主动调 `register_mtrack_debugger` 注册，平板用的是未改的 KGSL，模块侧补不了 |
| `/proc/ufs_oplus_dir/*` | 一加自家 UFS 驱动的接口，平板用联想的驱动，仅影响 `monitor_tool` 的存储遥测 |

## 已知问题

- **swap 占用仍低于对照机**。机制已查明：平板 swapd 被唤醒后有极高比例因
  "refault 太高"直接掉头不回收（修复前实测 5390/5409 ≈ 99.6%）。AOT 修好之后
  这个比例明显下降，但**尚无干净的稳态对照数据**，不在此宣称收益幅度。
- **`/data/misc/apexdata/com.android.art/dalvik-cache/` 仍为空**。原厂的 odrefresh
  路径被镜像里那批移植者产物堵死，只读分区删不掉，所以只能用绑定替代。镜像里
  因此白占约 340MB（system_ext）+ 60MB（my_stock）无法回收。
- **`oplus_synchronize` 仍不出货**，四轮四崩已结案，见 4.0.3 说明。
- **手势 CE 存储的 hook 需要手工勾选作用域**：`com.oplus.gesture` 未加入 LSPosed
  作用域时仍会 `FATAL`。
