# 4.1.0

把移植包里彻底断掉的 **KGSL 显存回收链**接了回来，并换上 r3 配套内核。
熄屏时实测释放约 450~510MB 不可回收显存，亮屏 2 秒内全部还原。

> 完整的定位过程、实测数据与两条走不通的实现路径见
> [r3 内核与 KGSL 桥验证](../investigations/r3-内核与KGSL桥验证.md)。

## 主要修复

### KGSL 显存永久不可回收

平板的 `Unevictable` 与 KGSL `page_alloc` 是 1:1（677MB 对 679MB），
对照机 PKX110 是 719MB 对 71MB。两台机器 GPU 内存总量相当，平板却把
100% 标成不可回收。桌面单进程用过一阵能涨到 470~1187MB，3GB 内存压力下
一个字节都不让，只有强杀进程才放得掉。

根因是链条第一环就断了：

```
没人写 /sys/class/kgsl/kgsl/proc/<tgid>/state
  -> 进程恒在 PINNED 态
  -> kgsl_reclaim_shrink_count_objects() 恒返回 0
  -> 内核永远不调用 scan_objects
  -> 显存永久不可回收
```

kprobe 实测：3GB 压力下 `count_objects` 被 `do_shrink_slab` 调用 **1328 次、
次次返回 0**，`scan_objects` 命中 **0 次**。手工写一次 `background`，count 立刻
返回 `0xc800`，scan 开始执行。**机制本身完好**，缺的只是那个厂商组件。

新增 `oplus_kgsl_state_bridge` 内核模块补上这个写入者：

- 只用 `filp_open`/`kernel_write`，等价于 shell 里 `echo background > state`。
  **不碰 `msm_kgsl` 的私有函数**——kprobe 取 `kgsl_proc_state_store` 地址再间接
  调用会被 kCFI 拒绝并 panic，而且 kobject 偏移只能靠猜。
- 触发点是**熄屏/亮屏**，不是 `oom_score_adj`。桌面的 adj 恒为 100，开应用、
  回桌面都不变，该 tracepoint 上涉及桌面的事件为 0 条；而能回收的量几乎全在
  桌面身上（adj>=700 的进程加起来只有 21MB）。
- 配套 `sepolicy.rule`。缺它 `filp_open` 返回 `-13`，实测 59 次写入全军覆没。

阈值与开关可在 `/sys/module/oplus_kgsl_state_bridge/parameters/` 运行时调整。

### `/dev/mqueue` 从未挂载

r3 内核开了 `CONFIG_POSIX_MQUEUE`，但 Android 的 init 不挂 mqueue。
4.0.4 加的挂载逻辑用了 `grep -q '\bmqueue\b'` 做能力检测——toybox 的 grep
不支持 `\b`，匹配恒空，于是每次开机都记下"内核不支持，跳过"，挂载从未执行。
改用 `-w` 整词匹配。至此 DroidSpaces 所需的内核能力齐全。

### BSP 包漏发 `sepolicy.rule`

`build_oplus_bsp.py` 用的是写死的文件白名单，新增的 `sepolicy.rule` 被静默
漏掉。改为模块根目录下的普通文件一律随包出货。

### 熄屏闸门从未闭合，以及它连带废掉的 HAL 控制

HybridSwap 的面板 kprobe 挂在 `panel_event_notification_trigger` 上，按
`notif_type` 1/2 读 blank/unblank。实测该函数在本机**只送 `notif_type=4`**
（FPS 变化，负载 144/120，正是这块 144Hz 屏的刷新率）。两路屏幕信号同时失效：

* `display_off` 从初值 0 起永远不变 —— 熄屏时该停的主动回收从未停过
  （`wakeup_swapd` 与 `swapd_shrink_node` 都靠它提前返回）；
* `hybridswapd_panel_bridge_active()` 只看 kprobe 注册标志，而注册确实成功，
  于是 `swapd_pause_store` 无条件清零并丢弃厂商 performance HAL 的写入。
  对照机 PKX110 的 `swapd_manual_pause` 是 2.27 亿次，平板修复前恒为 **0**。

改挂 msm_drm 的 `dsi_panel_power_off` / `dsi_panel_power_on`，并要求桥真的观测到
过一次转换才接管。冷启动后实测：亮屏 20 秒 `over_min_skip` +83,780，熄屏 20 秒
**+3**（停转），唤醒后 +4,328（恢复）。

> **教训**：判定一个探针"可用"要看它有没有真的收到过事件，不能只看注册返回值。

### KGSL 桥曾把待机内存换成了解锁卡顿

解锁窗口桌面的 95 分位帧时，熄屏回收过的两轮是 **101ms / 121ms**，没回收的那轮
只有 **24ms**。桌面是唯一的显存大户，也是解锁时第一个重画的东西；对照机在解锁
时桌面一帧都不重画。三项修正：

* 熄屏全量回收放过 `adj<0` 的常驻系统进程（SurfaceFlinger / system_server /
  SystemUI 正是画解锁动画的那几个）；
* adj tracepoint 回调也遵守熄屏状态 —— 此前它只看 `adj>=threshold`，桌面 adj
  一变就把扫描刚做的 background 写回 foreground，这正是"有时卡有时不卡"；
* 回收改为延迟触发，默认 **1800 秒**。这个数对齐原厂：OSense 的
  `sys_osense_memory_decisionmaker_config.xml` 里本来就有
  `<rule tag="delay" offset="1800000"><policy name="compress" type="screenoff"/>`。

修后三轮解锁桌面 95 分位 **8 / 5 / 5 ms、掉帧 0%**。

### 清掉不再需要的早期改动

* 删 `fix-module/module/bin/kgsl-state-sync.sh`（6 秒轮询的用户态同步器）及
  `service.sh`/`uninstall.sh` 里配套的清理段。那段**无条件**把所有 background
  还原成 foreground，会在 service.sh 阶段推翻内核桥刚做的判定 —— 是隐患而非兜底；
  桥自己 rmmod 时会还原。
* 删 `kernel-compat/oplus_hybridswap_panel_bridge/` 与其构建脚本：它挂的是同一个
  只送 FPS 事件的函数，从来没起过作用。

## 配套内核 r2

`boot-ACLaniakea-SM8650Q-droidspaces-r2.img`，需与
`vendor_boot-hyperSched-stub.img` **成对刷入**。

- `6.1.128-android14-11-sm8650q-droidspaces-r2`
- SysV IPC 走 `ANDROID_KABI_RESERVE` 预留槽，`module_layout` CRC 保持
  `0xea759d7f`；289 个 Lenovo/QTI vendor 模块静态检查 CRC mismatch 为 0
- Gloom / pcppages hook、32KB module percpu 预留
- 原厂 `TRIM_UNUSED_KSYMS` 与 BTF 配置不变

### 为什么不是 r3

本版开发过程中曾短暂用过 r3。r3 相对 r2 的**配置差异只有一行
`CONFIG_LOCALVERSION`**，唯一的实质改动是把 `filp_open`、`kernel_write` 加进
符号白名单——那纯粹是为 KGSL state 桥加的。桥既已移除（原因见下），这两个导出
就没有任何消费者，r3 相对 r2 不再提供任何东西，因此退回 r2。

本版的其余修复（HybridSwap 熄屏闸门、`/dev/mqueue` 挂载）都在**模块**里而不在
内核里，r2 上照常工作——已实机确认：内核 kprobe 注册表里有
`dsi_panel_power_off` / `dsi_panel_power_on`（均由 hybridswap 模块注册，标注
`msm_drm`），一次熄屏/亮屏各触发一次；490 个模块全部加载，0 熔断。

## 一条需要更正的历史结论

4.0.4 发布说明称"改为内核 kprobe 接 Lenovo 面板真实 blank/unblank 事件，
恢复 `display_off` 闸门"。本轮实测表明**这个结论不成立**：
`panel_event_notification_trigger` 在本机只送 FPS 变化事件
（`notif_type=4`，负载 144/120，正是这块 144Hz 屏的刷新率），从不送
blank/unblank。旁证是 `swapd_manual_pause` 在平板上恒为 0，而对照机
PKX110 是 2 亿次——手机在亮屏时暂停 swapd，平板从未暂停过。

本版的 KGSL 桥改挂 msm_drm 的 `dsi_panel_power_off` / `dsi_panel_power_on`，
实测每次屏幕转换各触发一次、无歧义。**HybridSwap 那条熄屏闸门也已在本版一并
修好**，见上面"熄屏闸门从未闭合"一节。

## 验证

安装并重启后：

```bash
# 桥已随 BSP 模块加载
adb shell su -c 'lsmod | grep oplus_kgsl_state_bridge'

# SELinux 放行已生效：failed 必须为 0
adb shell su -c 'cat /sys/module/oplus_kgsl_state_bridge/parameters/stat_failed'

# DroidSpaces 能力齐全
adb shell su -c 'grep -c " /dev/mqueue " /proc/mounts'   # 1
adb shell su -c 'ls /proc/sysvipc/'                      # msg sem shm

adb shell uname -r   # 6.1.128-android14-11-sm8650q-droidspaces-r3
```

熄屏约 4 秒后 `Unevictable` 应明显下降，亮屏 2 秒内回升。

冷启动实测：

| | 熄屏前 | 熄屏后 | 亮屏后 |
| --- | --- | --- | --- |
| `Unevictable` | 1194 MB | **745 MB** | 恢复 |
| `MemAvailable` | 1771 MB | **1965 MB** | — |
| 桌面 `state` | foreground | background（回收 199MB） | foreground |
| background 进程数 | 0 | 14 | 0 |

`writes=37 failed=0`，SELinux 拒绝 0 条，桌面同 pid 存活，屏幕正常唤醒。

## 已知上限

`max_reclaim_limit` 为 51200 页 = **200MB/进程**。桌面持有 827MB 时也只让出
199MB。抬高它可能多放出几百兆，但一次实测赶上基线自身在波动，数据不足以
下结论，暂时保留原厂值。
