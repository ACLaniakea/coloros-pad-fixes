# 4.1.1

> [!WARNING]
> **配套内核改为 r3，必须成对刷入 `boot-ACLaniakea-SM8650Q-droidspaces-r3.img` 与 `vendor_boot-hyperSched-stub.img`。**
> 本版 OPlus BSP 模块依赖 r3 才导出的 `filp_open`，**在 r2 上会加载失败**。
> `vendor_boot-ColorOS16-original-TB710FU.img` 仅用于回退原始 ColorOS 引导链，**不能**与本项目的 boot 混刷。
>
> ```bash
> adb reboot bootloader
> fastboot flash boot boot-ACLaniakea-SM8650Q-droidspaces-r3.img
> fastboot flash vendor_boot vendor_boot-hyperSched-stub.img
> fastboot reboot
> ```

修好**待机后动画卡顿**与**前摄指示灯失效**，重新接回 KGSL 显存回收链（按对照机
PKX110 的行为重做策略），把 HybridSwap 的 `swapd_pause`、swappiness 与 THP 三项
交还 ColorOS 原厂语义，并清零模块加载期与运行期的内核告警。

> [4.1.1 卡顿与内存回收排查](../investigations/4.1.1-卡顿与内存回收排查.md)，

## 主要修复

### KGSL 显存回收链接回，并且不再拿解锁动画买单

4.1.0 以"原厂不驱动、待机收益无人消费"移除了 KGSL state 桥。两机同负载对照推翻了
这两条理由：对照机的 `Unevictable` 在 30 次应用启动里恒为 **69MB**，平板是
**1.0~1.6GB**——联想这版 `msm_kgsl` 把显存 1:1 钉成不可回收，只能靠把进程标成
`background` 解钉；移植包缺了写这个节点的组件。对照机不需要，是因为它根本不钉。
消费者也不是"待机"，而是前台负载本身：平板 `allocstall` 约 800~1000 次/秒，对照机
20~114 次/秒。

开发中的 v4.1.1 桥改成 shrinker 驱动，但它的 `oom_score_adj` tracepoint 在 adj 变到
>=100 时就立即写 `background`，与压力无关。熄屏后桌面被锁屏遮住、adj=100，
**20 秒内 114MB 显存被整体回收**，解锁时从 zram 读回——这正是待机后动画卡顿。

出货的 v4.1.2 桥按对照机的行为定规则：

| 对象 | 何时标 background | 何时还原 |
| --- | --- | --- |
| adj < 0（SF / system_server / SystemUI） | 永不 | — |
| 缓存进程 adj >= 900 | 内存压力扫描 | adj 落回 900 以下 |
| UI 带 100 <= adj < 900 | 压力扫描，且亮屏、亮屏 30s 后、连续遮挡 >= 60s、显存 >= 192MB | **熄屏立即还原**；adj 变化时还原 |

壁纸、`com.oplus.blur`、输入法、侧边栏永远不碰；shrinker 回调里不做文件 I/O。
运行时参数在 `/sys/module/oplus_kgsl_state_bridge/parameters/`，说明见
`kernel-compat/kgsl_state_bridge/README.md`。

实机：熄屏 60 秒，压力扫描标记 15 个缓存进程，桌面（742MB）、壁纸、blur、SystemUI
`gpumem_reclaimed` 全为 0。

### 前摄指示灯失效：LSPosed 被钉回旧 Hook

机器上装有两份同 id 的 FixModule（正式安装 + 开发推送），两份都在 zygote 前把
LSPosed 模块路径钉到自己目录下的 APK，谁晚谁赢。开发推送带的是一份停在
2026-09-02 的 Hook，system_server 于是跑着 3.2 时代的钩子：没有前摄灯事件桥，
09-13 已撤回的"缓存进程上限 48"也回来了。

* `hook/versionCode` 改由 Hook manifest 生成（此前从 3.0 起一直是 301115，
  开机时的升级检查因此从未生效）；
* 路径同步工具发现当前钉住的是另一份仍启用、且版本不低于自己的模块副本时，
  拒绝改写并在日志里提示删除重复目录。

> 升级前请确认 `/data/adb/modules/` 下没有两个同为 `coloros_port_fix` 或
> `aclaniakea_oplus_bsp` 的目录。

### HybridSwap 与内存策略交还原厂

| 项 | 改动 | 依据 |
| --- | --- | --- |
| `swapd_pause` | 删除面板桥接管后永久清零的覆盖，恢复原厂 setter | 对照机：亮屏约 1.2s 后置 1、压住约 6s 放开；`swapd_manual_pause` 恒 0 -> 70s 内 +189,331 |
| zram_opt swappiness | 160/200 -> **125/125** | 对照机的编译期默认值 |
| THP | `always` -> **never** | 联想 vendor 启动脚本写 always，OPlus 写 never；`thp_fault_fallback` 406,637 -> 0 |

这三项在压力基准里**都没有可测的性能收益**，是保真修复，不是性能修复。

### 内核告警清零

* `oplus_cpu_sched_sched_info`：`hot_thread_node` 缓存带构造函数又用 zalloc 分配，
  触发 `mm/slub.c:2013` 告警，去掉构造函数。
* 11 条 `proc_dir_entry ... already registered`：多个一加模块各自创建
  `/proc/oplus_mem`、`/proc/task_info`，撞名即告警。改为先探测目录再创建；
  节点位置与改动前逐项一致。
* 仅剩联想原厂 `cps_wls_charger` 的一条 vendor 告警。

## 配套内核 r3

`boot-ACLaniakea-SM8650Q-droidspaces-r3.img`，需与 `vendor_boot-hyperSched-stub.img`
**成对刷入**。

- `6.1.128-android14-11-sm8650q-droidspaces-r3`
- 相对 r2 只多两个白名单导出：`filp_open`、`kernel_write`（KGSL 桥与 proc 目录探测使用）
- `module_layout` CRC 仍为 `0xea759d7f`；289 个 Lenovo/QTI vendor 模块 CRC mismatch 为 0

## 验证

安装并重启后：

```bash
adb shell uname -r      # 6.1.128-android14-11-sm8650q-droidspaces-r3
adb shell su -c 'grep -c . /proc/modules'                                          # 490
adb shell su -c 'cat /sys/module/oplus_kgsl_state_bridge/parameters/stat_failed'   # 0
adb shell su -c 'cat /sys/module/oplus_bsp_zram_opt/parameters/vm_swappiness'     # 125
adb shell su -c 'cat /sys/kernel/mm/transparent_hugepage/enabled'                 # [never]
adb shell su -c 'dmesg | grep -c "already registered"'                            # 0
```

打开前置相机，物理指示灯应亮起，关闭后熄灭。

## 已知限制

  `ui_min_mapped_mb` 或设 `ui_band_enabled=N`。
