# 一加内核模块移植到自建 GKI 6.1.128 的进度

日期：2026-08-26。全部结论来自真实编译，未上机。

## 一句话

**21 个一加内核模块已经在自建内核上编出 .ko，0 报错**；自建内核的
`uname -r` 与原厂逐字节一致，vendor ABI 门禁仍是 0 处 CRC 不匹配。

## 没编出来的，以及原因

| 模块 | 卡在哪 | 处理 |
| --- | --- | --- |
| `mm/hybridswap_zram` | 需要一加内核的 `OPLUS_MM_VH_*` 枚举；且与在用的标准 zram 互斥 | 不做，本项目一贯结论 |
| `mm/async_reclaim_opt/kshrink_lruvecd`、`pcppages_opt`、`gloom`、`memleak_detect` | 需要 GKI 里根本不存在的 mm vendor hook（`android_vh_do_page_trylock`、`drain_all_pages_bypass` 等），一加 common 树里也没有 | 要自己往 mm 热路径插钩子，风险高，暂缓 |
| `cpu/uad`、`cpu/cpufreq_bouncing` | 需要高通 `walt.h` 的结构体布局，必须与真机 walt.ko 完全一致，猜不得 | 不做 |
| `cpu/cpufreq_health`、`cpufreq_effiency`、`oplus_omrg` | 需要一加内核自带的 `linux/*.h`，源码包里没有 | 缺料 |
| `cpu/oplus_slc`、`cpu/midas/v1` | 联发科专用 / 老 `proc_ops` API | 不适用 |
| `cpu/sched/sched_tune` | 没有 `MODULE_LICENSE`，本来就是别的模块的一部分 | 归并问题，待查 |

## 为此改了内核什么

见 `patches/apply_oplus_hooks.py`，四处，全部通过门禁：

1. `android_vh_binder_proc_transaction_end`：声明 + 调用点 + 导出 + TRIM 白名单；
2. `struct binder_transaction` 加 `ANDROID_OEM_DATA_ARRAY(1, 1)`——
   一加 ipc 模块把 8 字节状态存在这里。**已核实 289 个联想 vendor 模块
   无一引用 binder 符号**，加字段不影响它们；
3. `CONFIG_LOCALVERSION` 设成 `-android14-11-g5c2cea985a84-ab13606743`，
   让 `uname -r` 与原厂逐字节相同。

## 模块侧的机械改写

见 `patches/port_oplus_modules.py`（幂等，可重复跑）：
`p->state` → `p->__state`、`task_running()` → `task_on_cpu()`、
`p->cpu` → `task_cpu(p)`、`mm->mmap/vm_next` 遍历 → maple tree 的
`for_each_vma()`、`page_referenced` 钩子改收 `folio`、
补 `linux/sched/cputime.h`。

**一条踩过的坑写在脚本注释里**：`android_oem_data*` 绝对不能改写成
`android_vendor_data*`。本内核 `CONFIG_ANDROID_VENDOR_OEM_DATA=y`，
两组数组同时存在，高通 WALT 占 vendor（`rq` 里只有 1 个 u64），
一加占 oem（`rq` 里 16 个）。改写不但编不过，编过了就是往高通的槽位里
塞 100 多字节——直接踩内存。

## 关于 vermagic 的一个发现

289 个联想模块的 vermagic 有三种：247 个 `-android14-11-maybe-dirty`、
38 个 `-g09833785ec0f`、4 个来自 `6.1.118`，**没有一个**等于真机
`/proc/version` 的 `-g5c2cea985a84-ab13606743`，但它们全都正常加载。
原因是开启 `CONFIG_MODVERSIONS` 后，`same_magic()` 会跳过版本号那一段，
只比后面的 `SMP preempt mod_unload modversions aarch64`。
所以自建内核不会因为版本串卡住 vendor 模块——尽管如此，
这一版还是把 `uname -r` 对齐成了原厂那串。

## 上机之前还差什么（重要）

1. **KernelSU 还没进这个内核。** 现在设备上的 fix-module / pen-bridge
   全部依赖 KernelSU，直接刷这个纯 GKI Image 会让它们一起失效。
   必须先把 KernelSU（或 SukiSU）合进源码再谈刷机。
2. boot.img 还没打包：需要原厂 boot 的 ramdisk + 这个 Image 重打。
3. 模块加载顺序与开关还没定：`sched_assist` 必须最先，
   `frame_boost` 之后；每个模块的 sysfs 开关默认值要逐个确认。
4. 回滚预案：U 盘工作区的 9008 包与原厂 boot 必须先确认可用再刷。

产物在 PC 的 `~/oplus-src/dist/`：`Image` 加 21 个 `.ko`，共 54 MB。
