# 自建内核刷机：事故复盘与救援手册

2026-08-27 凌晨，一次内置版内核把 A 槽刷成不可引导，最终用 9008 救回。
全过程记在这里，重点是**当时判断错在哪**。

## 一、事故经过

把 21 个一加模块 built-in 进 vmlinux 的那一版，编译通过、vendor ABI 门禁
0 处不匹配、`uname` 版本串正常，但刷进去**起不来**（initcall 阶段）。

真正把事情放大的不是这个内核，而是接下来的连锁反应：

1. bootloader 连续 6 次引导失败后，把 A 槽标记为 `slot-unbootable:a: yes`；
2. 之后每次开机都直接掉进**一个受限的"救援 fastboot"**；
3. 在这个受限模式里刷不回去——而我们一开始完全没意识到它是另一个 fastboot。

## 二、怎么一眼认出"救援 fastboot"

**三个特征同时出现，就是它：**

| 现象 | 受限救援 fastboot | 正常 bootloader fastboot |
| --- | --- | --- |
| `getvar partition-size:boot_a` | `0` 或 `unknown command` | `0x6000000` |
| `getvar max-download-size` | 查不到 / `unknown command` | `805306368` |
| `set_active a` | `FAILED (Invalid Slot)` | OKAY |
| 大镜像下载 | `Requested download size is more than max allowed` 或直接卡死 | 正常 |

**`partition-size` 报 0 是最快的判据。** 看到它就该立刻明白：
不是线坏了、不是镜像大了、不是 U 盘卡了——**是对面这个 fastboot 是残废的**。

当晚我先后怀疑过数据线、USB 口、exFAT 的 fuse 卡顿，全都猜错，
浪费了很久。真正的反证一直摆在眼前：同一台机器同一根线，
用 `fastboot reboot bootloader` **显式**重进 bootloader 之后，
`max-download-size` 立刻正常报出 768 MB。物理链路从来没问题。

## 三、救援：9008 只写一个分区

包：`ColorOS16.0.8.301_A16_TB710FU[97d558].zip`
（`bin/9008/prog_firehose_ddr-TB710FU.melf` + `images/boot.img` + rawprogram*.xml）

**绝对不要跑整包刷写**——那会连 super 和 userdata 一起冲掉，
这个项目几个月的 KernelSU 模块、LSPosed 配置、pen-bridge 全没。
坏的只有 boot_a 一个分区，就只写它。

boot_a 的几何（来自 `images/rawprogram4.xml`）：

```
physical_partition_number=4   start_sector=112006
SECTOR_SIZE=4096              num_partition_sectors=24576   (96 MB)
```

工具用 bkerler 的 edl（Arch 上 `pip` 不在 PATH，要建 venv 装 git 版）：

```sh
python3 -m venv ~/edlvenv
~/edlvenv/bin/pip install "git+https://github.com/bkerler/edl.git"

E=~/edlvenv/bin/edl
L=~/edlwork/prog_firehose_ddr-TB710FU.melf
sudo $E w boot_a ~/stock-boot.img --loader=$L --memory=ufs
sudo $E reset --loader=$L
```

写回去的 `images/boot.img` 与当晚从设备 dd 出来的备份 **sha256 完全一致**，
所以确实是原本那份东西。写完设备就能正常开机，失败计数随之清掉。

## 四、我在救援过程中做砸的一步

想顺手清掉 misc 里的 `bootonce-bootloader`（`fastboot reboot bootloader`
留下的一次性标志），流程是 dump → 改 → 写回。但 `edl r` 是以 root 跑的，
dump 出来的 `misc.bin` 属主是 root，改写脚本以普通用户身份运行 →
`PermissionError`，**脚本报错了但后面的写回照跑**，把没改过的 misc 又写了回去。

结果：那一步等于白做，真正让机器活过来的只是 boot_a 写回原厂。
残留的标志后来是在系统起来之后用 root 直接清的：

```sh
su -c 'printf "%.0s\0" $(seq 1 32) | dd of=/dev/block/by-name/misc bs=32 count=1 conv=notrunc'
```

**教训**：管道里一步失败不能让后续步骤继续跑；涉及分区写入的脚本
必须 `set -e` 或显式检查上一步的返回值。

## 五、以后测试实验内核的正确姿势

**别再直接 flash 了，用 `fastboot boot`：**

```sh
adb reboot bootloader          # 从正常系统进，拿到完整的 fastboot
fastboot boot ~/experimental-boot.img
```

`fastboot boot` 只把镜像下载到内存里引导一次，**完全不碰 boot_a**。
起不来就断电重启，设备照样从原来的 boot_a 正常开机——
不会累计失败次数，不会把槽标死，也就不会掉进救援 fastboot。

确认能起来、能用之后，再 `fastboot flash boot_a` 落盘。

其余纪律：

- 每次实验前确认 `kernel-backup/` 里有当前可用的 boot 镜像；
- 实验版起不来时**不要反复重启让它自己重试**——立刻断电，
  用 `fastboot boot` 或从正常 fastboot 刷回，别把 6 次重试用光；
- 一旦看到 `partition-size` 报 0，先 `fastboot reboot bootloader`
  显式重进一次，再判断问题。

## 六、完整的救援配方（两次事故验证过）

**顺序不能变，缺一步都不行：**

```
1. 9008 里写回原厂 boot_a
   sudo edl w boot_a stock-boot.img --loader=prog_firehose_ddr-TB710FU.melf --memory=ufs
   sudo edl reset --loader=prog_firehose_ddr-TB710FU.melf

2. 设备复位后会停在 fastboot（reset 打的 USBError 是正常现象，不代表没退出）

3. ★ fastboot set_active a          ← 真正让机器活过来的就是这一条
      它把 slot-unbootable:a 从 yes 改成 no，retry-count 从 6 复位到 7

4. fastboot reboot，然后拔掉数据线
```

**第 3 步是整个流程的核心。** 光写回 boot_a 没用——槽还被标死，
bootloader 照样不引导它。

### 我在这里判断错了两次，都记下来

**第一次**：EDL 写完 boot_a 之后机器起来了，我以为是"写回镜像 + 拔线"救的，
**没意识到中间那个 `fastboot set_active a` 任务其实执行成功了**
（我误以为它被打断没跑）。于是第二次事故时我照着错误的经验来，
让用户反复拔线试，白折腾了一轮。日志里写得清清楚楚：

```
slot-unbootable:a: yes  →  Setting current slot to 'a'  OKAY  →  slot-unbootable:a: no
                                                                 ✅ 开机完成（约 78 秒）
```

**教训**：救援成功之后要回去把日志读完，确认到底是哪一步生效的，
不能凭印象归因。凭印象归因的代价是下一次照着错的做。

**第二次**：`fastboot set_active a` 在残废会话里会直接报
`fastboot: error: Device does not support slots`——因为该会话连
`has-slot` / `current-slot` 都答不出来，客户端就认定这机器没有 A/B，
命令根本没发出去。**这时不要在 fastboot 里硬试**，回 9008 用
`edl setactiveslot a` 直接改 GPT 属性位。

### fastboot 会话能力是会变的

同一台设备、同一根线，不同时刻进的 fastboot 能力天差地别：

| 进入方式 | partition-size | slot 相关 getvar | set_active |
| --- | --- | --- | --- |
| 从正常系统 `adb reboot bootloader` | 正常 | 正常 | OKAY |
| EDL 写完 boot_a 后复位进入 | 正常 | 正常 | OKAY |
| 引导失败自动掉入（救援模式） | 0 或 unknown | 全部查不到 | Device does not support slots |

**判据**：`getvar slot-unbootable:a` 答不出来 = 残废会话，别浪费时间。

## 七、`fastboot boot` 在这台机器上用不了

试过了：`Sending 'boot.img' FAILED (Status read failed (No such device))`,
设备在传输中途直接掉线。原因是 GKI 的 ramdisk 拆分布局——
本机 `boot.img` 里 `ramdisk size: 0`，真正的 ramdisk 在 `init_boot`，
第一阶段的在 `vendor_boot`。bootloader 拿到一个没有 ramdisk 的
自包含镜像，没有拼装逻辑，直接崩掉。

**所以"内存引导验证、失败零代价"这条路在这台机器上不成立。**
未验证的想法：用 `mkbootimg` 把 `init_boot` 的 ramdisk 拼进测试镜像，
让它变成真正自包含的镜像再试。

## 八、built-in 路线的结论

两次尝试，两次都要 9008 救：

1. 21 个一加模块全部 built-in（`module_init` = `device_initcall`）→ 起不来；
2. 只内置 `sched_assist` 一个、且改成 `late_initcall` → 照样起不来。

**所以根因既不是"一次编太多"，也不是初始化时机。** 结合之前
insmod 真模块时当场 Oops（`Unable to handle kernel paging request`），
可以确定是**一加 sched_assist 与联想 hyperSched 在同一批 rvh 钩子、
同一块 `rq->android_oem_data1` 上真的撞车**，built-in 只是把撞车时刻
从 insmod 提前到了开机。

**在解决"联想那份怎么让位"之前，不要再往 boot_a 里刷内置版。**

## 九、B 槽当试验田——此路不通，但验证了回落机制

设想：把实验内核刷进 `boot_b`，`set_active b`，失败时 bootloader 自动回落到 A。
实测**不可行**，原因是 super 里没有 `_b` 那套逻辑分区：

```
init: DM_DEV_STATUS failed for system_b: No such device or address
init: Failed to mount /system: No such device or address
Kernel panic - not syncing: Attempted to kill init!  (sys.boot.reason=kernel_panic,init)
```

我此前把 `getvar has-slot:system:no` 理解成"两槽共用 system"，**这是误读**——
那句话只说明 system 不是物理分区。它作为 super 里的逻辑分区照样分槽，
而移植系统只灌了 `_a` 一套。补齐 B 要往 super 里再塞一整套逻辑分区
（约 8 GB + lpmake），不现实。

### 但这一轮换来三条有用的结论

**1. A/B 回落机制确实工作。** B 起不来之后，bootloader 耗完重试自动回到 A，
正常开机、457 个模块、零干预。**今晚两次 9008 本来都可以这样避免**——
只要实验对象不是唯一可引导的那个槽。

**2. 物理分区里 A 和 B 只有 `boot` 不同**，其余 33 个全部一致：

```
abl aop aop_config bluetooth cpucp devcfg dsp dtbo featenabler hyp imagefv
init_boot keymaster modem multiimgoem multiimgqti pvmfw qupfw qweslicstore
recovery shrm spuservice tz uefi uefisecapp vbmeta vbmeta_system vendor_boot
vm-bootsys xbl xbl_config xbl_ramdump
```

所以"B 槽坏了"的说法不准确，坏的只是 super 里缺 `system_b`。

**3. pstore 能拿到失败启动的完整 console。**
`/sys/fs/pstore/console-ramoops-0` 保存上一次启动的内核日志。
这次的死因就是直接从里面读出来的。
**以后每次实验失败，第一件事就是读它**——不要像今晚前两次那样
反复重启、反复刷，把唯一的证据冲掉。

## 十、既然没有安全试验田，实验纪律改成这样

刷实验内核进 `boot_a` 之前：

1. 确认 `kernel-backup/` 里有已验证可用的 boot 镜像，且 `~/stock-boot.img` 在位；
2. 刷完盯着，**第一次起不来就立刻按 音量下+电源 强制进 fastboot**——
   不要让它自己重试。此时 slot 还没被标死，会话是完整的，
   一条 `fastboot flash boot_a` 就能刷回去，用不着 9008；
3. 刷回去之后**先开机、先读 pstore**，再想下一步。

只有在"已经让它重试到掉进救援 fastboot"的情况下才需要 9008，
而那种情况本身就是操作失误。

### 补充：为什么不给 B 槽灌逻辑分区

查明这机器是 **Virtual A/B**（`ro.virtual_ab.enabled=true`，
lpdump 里 `Header flags: virtual_ab_device`）。super 共 19 GB，
`_b` 那组逻辑分区在元数据里**声明了但 Extents 为空**——
这不是损坏，是 Virtual A/B 的设计：B 槽逻辑分区只在 OTA 时
以快照形式临时物化，合并后 B 即成为新的 A。

技术上可以用 fastbootd 手动灌（dump A 的 7 个逻辑分区再
`fastboot flash system_b` 等），但那要改 super 的元数据——
**super 正是承载移植系统的分区**。为了一个试验田去动它，
风险大于它要防的风险。

**决定：不做。实验仍然刷 boot_a，靠 9008 兜底。**
EDL 单分区救援已跑通两次，全流程约三分钟，不丢数据。
